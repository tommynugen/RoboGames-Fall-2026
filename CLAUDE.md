# CLAUDE.md

A Gazebo sim for the ROBOGAME-2.0 robots: ROS 2 Lyrical, Gazebo Jetty
(gz-sim 10), one ament_python package, `src/robogame_sim`, and
`src/robogame_gui`, a small C++ Gazebo GUI plugin (the Camera view card).
The remote is github.com/tommynugen/RoboGames-Fall-2026, which is public:
keep machine paths, keys and personal details out of commits. README.md is
the full manual: what each launch argument does, how the chase and planner
behave, the layout file format, and what was checked in Gazebo and when.
Read the section you need rather than the whole file.

## Commands

```
source /opt/ros/lyrical/setup.bash && colcon build --symlink-install && source install/setup.bash
cd src/robogame_sim && PYTEST_DISABLE_PLUGIN_AUTOLOAD=1 python3 -m pytest test   # tests, no Gazebo
python3 -m robogame_sim.chase_sim mazetest default --seeds 4                     # chase in 2D, from src/robogame_sim
ros2 launch robogame_sim sim.launch.py gui:=false fpv:=false speed:=0 step:=0.002 layout:=NAME robots:=1,2 chase:=1,2
ros2 run robogame_sim robot_console                                              # the robot console, beside a sim
scripts/gazebo_chase_suite.sh /tmp/chase_runs [SCENARIO]                         # 14 test4 runs, a few minutes
```

Gazebo and launch output is long: send it to a file and grep or tail it, or
run it in the background. A run left behind blocks the next one ("Another
world of the same name is running"): `pkill -x gz-sim-main`. The
`parameter_bridge` segfault at shutdown is a known upstream bug; ignore it.

## Where things are

All in `src/robogame_sim/robogame_sim/` unless given.

| File | |
| --- | --- |
| `terrain.py` (1150 lines) | height map from the arena's collision geometry, A* planning, path smoothing. Almost all of it is `class Terrain` |
| `chase.py` | `Chaser`, the hunter's steering: target tracking, standoff, drive commands |
| `chase_node.py` | ROS node around `Chaser` |
| `chase_sim.py` | 2D stand-in for Gazebo to try `Chaser` against moving targets |
| `arena_layout.py` (890 lines) | layout JSON load/save, `PARTS`, `check()` (the editor's red outlines), world SDF building, spawn spots |
| `arena_editor.py` + `arena_editor.html` | the layout editor at localhost:8766; the html is one big file, grep it. Its module drawing is in `arena_draw.js`, shared with the console |
| `sim_firmware.py`, `firmware_model.py` | stand in for the ESP32 firmware and BLE bridge |
| `racing_teleop.py`, `drive_controls.py`, `motion_sensor.py` | PS4/PS5 racing controls and wheel steering |
| `controller_robots.py`, `gamepads.py` | a robot for every controller connected (hotplug); takes rebinds from the console |
| `robot_console.py` + `robot_console.html` | the robot console at localhost:8767: bind controllers, make robots autonomous, send them places |
| `autopilot.py` | the console's driving: command queue and chase mode, on `Chaser` |
| `active_arena.py` | publishes the arena in use on `/arena/layout`, latched; the sim launch starts one |
| `robot_sdf.py`, `spawning.py`, `fpv_toggle.py` | robot model, spawn placement, FPV camera and the 1 to 4 views |
| `src/robogame_gui/src/RobogameView.*` | the Camera view card in the Gazebo side panel, talks to `fpv_toggle` |
| `launch/sim.launch.py` | the one launch file; checks its arguments |
| `layouts/*.json` | arena layouts, one module per line |
| `scripts/` | Onshape export, Gazebo chase suite and scoring, arena_perception sync |

Big files not worth reading whole: `models/robogame_arena_cad/model.sdf`
(88 KB, generated by `scripts/export_onshape_arena.py`), the STL meshes,
`arena_editor.html`. Grep them, or read a line range.

`src/arena_perception/` is a copy of the ROBOGAME-2.0 package made by
`scripts/sync_arena_perception.sh`. Never edit it; a sync overwrites it.
The ROBOGAME-2.0 checkout itself is only ever read.

## Conventions

- Write README, comments and commit messages in plain English, as the
  existing ones are: short words, no jargon, units given.
- Behaviour changes go in README.md too, with a dated "Checked ..." note
  saying how they were verified (tests, `chase_sim`, headless Gazebo).
- Commit messages: an imperative headline saying what the robot or tool
  now does, then paragraphs on why and what was checked.
- Run the tests before committing. For planner or chase changes, also
  run `chase_sim`, and for anything about climbing or gaps, the Gazebo suite.
